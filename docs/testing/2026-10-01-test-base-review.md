# Test-base review — 2026-10-01

Review of the whole test base against the backlog's acceptance criteria (AC), the user flows E2E walks, and a mutation analysis of how the tests react to injected bugs. Follow-up PRs: #214 (mutation guards + shopping-list fix), #215 (API boundaries), #216 (phone journeys, assertions that could not fail, focus and colour guards).

## Summary

- **192 stories and bugs** with AC (Done / In review / In progress) mapped to the tests that verify them, by layer.
  - covered: 154
  - partial: 17
  - not implemented / no test: 4
  - AC drift (stale text): 8
  - visual only: 5
  - manual / CI config: 4
- **Not implemented although the story is Done** (filed as backlog bugs): the cook timer gives no alert at 0:00; owner can't change roles and members can't leave a household; no 'copy shopping list'; no cooking streak; no nutrition preview on the pick screen; no home dietary filter; the configurator's usage badge and per-tab create are missing.
- **Mutation testing** (Stryker, run outside the repo): shared 67%, app utils 92%, MCP tools 65%, API middleware + routes (unit layer) 77%. The worst gap was the allergen table (31%): whole allergens could be emptied with no test failing. It is now pinned term by term.
- **Bug found by a mutant:** the shopping list dropped a measured ingredient when another recipe listed it 'a gusto' in the same unit (fixed in #214).

## Layers and how to read the matrix

Layers: unit, int (Postgres integration), screen (jsdom), e2e (Playwright), ci (a CI job is the check). 'Partial' means at least one AC clause has no test or the behaviour is missing. 'Drift' means the AC text no longer describes what shipped.

## E2E user-flow review (21 specs, 267 tests)

## Overall

- ~40% of E2E tests are presence checks ("shows X button", "shows title") duplicated across smoke/menu/weekly-menu specs; they prove a screen renders, not that a person reached a goal.
- Specs are organised by coverage motive (coverage-gaps, coverage-round4: 69 tests) instead of user journeys; branch-chasing via route interception is valid but belongs with the journey it protects.
- Only Desktop Chrome runs. The audience plans and cooks on a phone; only one test (390px form) uses a phone viewport.
- 5 either/or assertions can't fail in practice: "shows items or empty state", "empty or list state", "create or existing household", "empty state or past sessions", "recipe list or empty state".

## Journeys a real user does that no test walks end to end

1. Organizer week (phone): plan 3 days → shopping list shows the AGGREGATED quantities (e.g. 2 recipes with cebolla → one line with the sum) → tick items → pantry "Ya tenés" → cook a planned dish → mark it cocinado → stats count it. Pieces exist separately; the aggregated quantity is never asserted in the UI.
2. Household, two people: owner invites by email → invitee accepts → invitee (member, not viewer) sees the shared recipe AND adds to the shared menu → owner sees it. Only the viewer variant exists (1 test).
3. Agent-first path: MCP tool creates a recipe (or imports from a URL) → it shows up in the app with nutrition, diet tags and provenance. import.spec creates through the API directly, so the MCP→app path is never exercised.
4. Nutrition goal loop: set daily + per-meal goals → plan → see the delta turn ámbar/terracota → swap a dish → back to salvia. Steps are tested as isolated widgets.
5. Cooking a timed step: timer reaches 0 → user is alerted. The test only checks the timer resets; the alert itself does not exist (AC #136).
6. Deleting a recipe that is planned and has history: menu keeps the title snapshot, history keeps the session (covered at integration, not in the UI).
7. Real edit: change a title/quantity and see it everywhere (detail, planner chip, shopping list). Avoided because tests share seeded recipes; needs per-test fixtures.

## Weak or misleading tests

- "a step timer pre-loads, taps to start, and runs to completion": asserts the reset, no completion feedback.
- "creates a recipe and it appears in the list": OK, but never opens it to verify ingredients/steps were saved as typed.
- visual-tour: screenshots only, no assertion — fine as an artefact, not as coverage.

Closed in #216: journeys 1 and 2 (organizer week on a phone; two-person household), the five either/or assertions, and the search-focus and hex-colour guards. Journeys 3–7 are tracked in the backlog chore 'remaining test-base gaps'.

## How to rerun

- Matrix: query the backlog for stories/bugs with AC, then search the tests per AC (this file is the baseline to diff against).
- Stryker without adding dependencies: install `@stryker-mutator/core`, `@stryker-mutator/vitest-runner` and `typescript` in a scratch directory, symlink the repo's `vitest` into it, and run with `inPlace: true` and the plugin's `dist/src/index.js` path. Use `ignoreStatic: true` for the API (route definitions are static mutants).
